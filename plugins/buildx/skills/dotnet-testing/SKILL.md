# .NET Testing — Authoring Reference

L1 dispatcher. Concrete chapters live in L2 sub-files.

## Mental model

Testing on this team is **real integration testing only**, against the **real Aspire-orchestrated topology**, from **one** test project per product. The test exercises the same object graph that ships to production — no in-memory swaps, no DI mocks, no hand-rolled fakes implementing production ports, no behaviour-forking environment branches. Containers and projects are real. Stubs for third parties (Stripe, Twilio, partner APIs) are real ASP.NET Core projects, registered in the AppHost like any other resource. Every test reaches the system through an **executable surface the AppHost declares** — if a behaviour cannot be reached that way, the flow (or the production surface) is mis-modelled; an in-process "guard" test is never the answer.

Fixture discipline is **one centralized base, one fresh AppHost per class**: a single `AppHostFixture` base class owns the mount/dispose lifecycle via `[ClassInitialize(InheritanceBehavior.BeforeEachDerivedClass)]` / `[ClassCleanup(InheritanceBehavior.BeforeEachDerivedClass)]`; every test class that exercises the system inherits it. Each derived class still gets its own `DistributedApplication` — centralization is about the code living in ONE place, not about sharing a host. No class mounts a host outside the fixture; no `[AssemblyInitialize]` mounts the system-under-test. The cost of one AppHost per class is paid intentionally — debuggability and isolation outweigh boot overhead.

## Ownership

Tests are authored by `dotnet-test-designer`, not by `dotnet-developer`. The 1:1 correspondence with flows is non-negotiable: every `FL-NNN-*.md` under `docs/features/FT-*/flows/` has a `## Test` block whose `FQN` field points to exactly one test method in this project. When a flow changes shape or a new flow is added, the test-designer is dispatched to write / extend the test BEFORE the developer touches production code. See agent `dotnet-test-designer`.

## Non-negotiable rules (must survive compaction)

1. **Single test project.** Exactly one `[Company].[Product].Test` (singular `Test`, never plural `.Tests`, never `.UnitTests` / `.IntegrationTests` / `.E2ETests` / `.WebTests` / `.Smoke` / `.Acceptance`). Lives under `test/[Company].[Product]/[Company].[Product].Test/`, never under `src/`. See [layout.md](layout.md).
2. **MSTest only.** xUnit, NUnit, bUnit are not used. Pin the unified `MSTest` package ≥ 4.0.x.
3. **Real integration tests only — no unit tests, ever, under any label.** Every test exercises a real surface: HTTP through the Aspire AppHost, Playwright against the running UI, real gRPC client, real CLI invocation, real queue / event triggers. In-process "guard" / "composition" / "parity" / "contract" tests (DI-validation checks, serializer round-trips, template renders with in-test stores, host-builder assertions) are unit tests wearing a costume — banned. "Is this integration or end-to-end?" is an unproductive debate; if a behaviour cannot be exercised through a real surface, the flow itself is mis-modelled — escalate to `analyst`. See [forbidden-patterns.md](forbidden-patterns.md) § in-process guard tests.
4. **One canonical `AppHostFixture` base; one fresh AppHost per class.** A single base class in the test project root owns mount (`[ClassInitialize(InheritanceBehavior.BeforeEachDerivedClass)]`) and dispose (`[ClassCleanup(InheritanceBehavior.BeforeEachDerivedClass)]`). Every system-exercising `[TestClass]` inherits it; each derived class gets its OWN `DistributedApplication` — no host is shared across classes. **No second fixture, no ad-hoc self-mounting class, no `[AssemblyInitialize]` hosting the system-under-test.** `[AssemblyInitialize]` is permitted ONLY for suite-wide setup that does NOT mount the system-under-test (e.g., Playwright auth-state generation against a short-lived auxiliary AppHost; pre-computing reference data files). See [mstest-integration.md](mstest-integration.md).
5. **Surface folders are derived from the AppHost's executables.** The folder set inside the test project mirrors the executable resources the AppHost declares (and `docs/SOLUTION.md` lists): a web UI → `UI/` (plus `HTTP/` if it exposes an API), an API service → `HTTP/`, a gRPC service → `Grpc/`, a CLI → `Cli/`, a worker → `Worker/` (timer/hosted trigger) or `Queue/` (message trigger), inbound webhooks → `Webhook/`. There is **no `Service/` folder** — a surface folder with no matching executable is a defect. One `[TestClass]` per area, file name `{Area}_Tests.cs`, method names `{Action}_{Scenario}_{Expectation}`. See [layout.md](layout.md).
6. **No mocks — third-party OR hand-rolled.** `Moq`, `NSubstitute`, `FakeItEasy`, `WireMock.Net` are banned in `[Company].[Product].Test.csproj`, AND no class inside the test project may implement a production port / interface (an in-test `FakeXxxStore : IXxxStore` is a mock by another name; an in-process `HttpListener` sink is a stub project that refused to be one). When a third party has no native emulator, ship a real stub project and register it in the AppHost. See [forbidden-patterns.md](forbidden-patterns.md).
7. **No test-specific code paths in production.** No `if (env.IsEnvironment("Testing")) …`, no `#if INTEGRATION_TEST`, no `services.AddSingleton<I…, Fake…>()` guarded by an environment check, no `MapPost("/_test/seed", …)` / `/_test/reset` endpoints, no `DbInitializer` hosted service that loads fake data, no EF Core `UseSeeding` lambda inserting "Demo User". The app behaves identically in dev, tests, and prod. See [forbidden-patterns.md](forbidden-patterns.md).
8. **Ephemeral resources, always.** No `WithDataVolume()`, no `ContainerLifetime.Persistent`, no `WithBindMount` on data folders. Every run starts from a blank container. See [seeding.md](seeding.md) § Invariants.
9. **Seed code lives in the test project**, under `Seeding/`. One file per concern (`SqlSeedData.cs`, `CosmosSeedData.cs`), `internal static class`, `internal static async Task ApplyAsync(...)`, idempotent. Pick the strategy per resource. See [seeding.md](seeding.md).
10. **MSTest class-level parallelism is hostile to AppHost suites.** Two classes booting AppHosts simultaneously fight for the same emulator ports. Pin `[assembly: Parallelize(Workers = 1, Scope = ExecutionScope.MethodLevel)]` in `AssemblyInfo.cs`. See [mstest-integration.md](mstest-integration.md) § Parallelism.
11. **`WaitForResourceHealthyAsync` timeouts ≥ 3 minutes** for any cloud/emulator resource. The default 30 s frequently flakes on cold-starting Service Bus / Cosmos / SQL emulators.
12. **One suite, one code path — emulators ARE real infra; topology is wiring, not code.** No `[TestCategory]` tiers (`RealInfra`, `Slow`, `Nightly`), no gated CI jobs, no behaviour forks, no test that reaches a service the AppHost does not orchestrate. Running the SAME full suite against provisioned (non-emulated) infrastructure IS permitted under exactly one condition: neither application nor test code changes in function of it — only the args handed to `DistributedApplicationTestingBuilder.CreateAsync`, assembled in the single consolidated `TestSettings.cs` from `TESTRUN_*` env vars (topology + run-behaviour knobs: headed, slow-mo, timeouts — never assertions). With zero env vars set the suite runs anywhere with zero secrets; SDKs that pin vendor hostnames are wired to stubs at the DNS level. `TestSettings.cs` is the only file allowed to read env vars. See [mstest-integration.md](mstest-integration.md) § One suite, one topology and § TestSettings.
13. **ALL artefacts consolidate under `TestContext.TestRunResultsDirectory`; shared auth state under `TestResults/.auth/`.** Per-run transients (logs, traces, screenshots, video, trx, coverage, recorded payloads) land under `TestContext.TestRunResultsDirectory` (fallback: `Path.Combine(AppContext.BaseDirectory, "TestResults")`), per class under `logs/{ClassName}/` etc. **In-repo artefact folders (`tests/automated/`, repo-root session files, anything git-adjacent) are banned**, and so are path-override env vars (`BLAZTRAP_TEST_RUN_DIR`, `*_LOG_DIR`) — MSTest's `TestContext` is the single source of truth. Authentication state files (`{role}-state.json`) are shared across runs and live at `TestResults/.auth/`, computed as `Path.GetDirectoryName(TestContext.TestRunDirectory)` + `/.auth/` (fallback: `Path.Combine(AppContext.BaseDirectory, "TestResults", ".auth")`); they are generated unattended — a test that needs a human operator to complete sign-in is a defect. Per-resource AND AppHost logs come from `Blaztrap.Aspire.FileLogging` (`appHost.AddFileLogging(logsDir)` after every `AddProject`/`AddExecutable` and before `Build()`); the legacy `Blaztrap.Aspire.Testing.FileLogging` package and its `AddResourceFileLogging` are banned — they drop `apphost.log`, where startup failures land. See [mstest-integration.md](mstest-integration.md) § Test artefacts.

## Quick decision matrix

| Need | Pick |
|---|---|
| Brand-new test project | [layout.md](layout.md) — single `[Company].[Product].Test`, surface folders derived from the AppHost's executables, MSTest. |
| Add a new test class | One `[TestClass]` per area, file `{Area}_Tests.cs` under the matching surface folder, inheriting the canonical `AppHostFixture`. |
| Pick a test method name | `{Action}_{Scenario}_{Expectation}` — e.g. `CreateOrder_WithValidData_ReturnsCreated`. |
| Seed test data | [seeding.md](seeding.md) — direct client (SQL/Mongo/Redis/Kafka) / `WithInitFiles` (Postgres) / emulator+SDK (Azure) / eventing subscriber (cross-resource or HTTP-driven). |
| Capture per-resource + AppHost logs | `appHost.AddFileLogging(logsDir)` from `Blaztrap.Aspire.FileLogging` (NEVER the legacy `Blaztrap.Aspire.Testing.FileLogging`). See [mstest-integration.md](mstest-integration.md). |
| Suite is flaky / class-level races | Pin `[assembly: Parallelize(Workers = 1, Scope = ExecutionScope.MethodLevel)]`. See [mstest-integration.md](mstest-integration.md) § Parallelism. |
| Tempted to mock a dependency (library OR hand-rolled fake) | Don't. Ship a stub project and register it in the AppHost. See [forbidden-patterns.md](forbidden-patterns.md). |
| Tempted to write an in-process "guard" / composition / parity test | Don't. Reach the behaviour through a real surface, or escalate the missing surface. See [forbidden-patterns.md](forbidden-patterns.md). |
| Tempted to write logs / recordings to an in-repo folder | Don't. Everything under `TestArtifacts.RunDir(context)`. See [mstest-integration.md](mstest-integration.md) § Test artefacts. |
| Tempted to add `if (Testing) seed…` in `Program.cs` | Don't. Move to a seeding strategy in the test project. See [forbidden-patterns.md](forbidden-patterns.md) and [seeding.md](seeding.md). |
| Test needs a real external service (ARM, Graph, mail, partner API) | It doesn't — the AppHost is missing an emulator or stub project; SDKs that pin hostnames get DNS-level wiring. See [mstest-integration.md](mstest-integration.md) § One suite, one topology. |
| Run the suite against provisioned (non-emulated) infrastructure | Same full suite, no filter, no code change — set the `TESTRUN_*` env vars consumed by `TestSettings.AppHostArgs()`. See [mstest-integration.md](mstest-integration.md) § TestSettings. |
| Add a run knob (headed browser, slow-mo, timeout ceiling) | One place only: `TestSettings.cs` + `TESTRUN_*` env var with a zero-setup default. Knobs change wiring/observability/pace, never assertions. |
| Tempted to add a `[TestCategory]` tier (RealInfra, Slow, Nightly) | Don't. One suite, one code path — switch topology via `TestSettings`, never via taxonomy. See [mstest-integration.md](mstest-integration.md) § One suite, one topology. |
